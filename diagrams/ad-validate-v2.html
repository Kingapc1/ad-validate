01 / Flowchart

Precondition gate — ลำดับบังคับใน New Job ก่อนกดปุ่ม Validate

ทั้งหมดนี้เกิดขึ้นในหน้า New Job ก่อนกดปุ่ม Validate — ไม่ใช่กดเข้า Ad Validate แล้วค่อยมาเจอว่าข้อมูลขาด · ของเดิมบังคับแค่ว่า Business และ Contact ต้องครบจนหลอดเขียวเต็ม แต่ไม่เคยบังคับลำดับ MCC จะทำอันไหนก่อนก็ได้ · flow ใหม่บังคับลำดับเป็น Contact ก่อน แล้วค่อย Business โดย Contact เองมี 2 ขั้นที่ต้องทำเรียงกัน และขั้นถัดไปถูกล็อกจนกว่าขั้นก่อนหน้าจะสำเร็จ

ประเด็นพฤติกรรมเดิมพฤติกรรมที่ต้องปรับ
ลำดับการทำ ทำ Business หรือ Contact ก่อนก็ได้ ระบบไม่สนใจลำดับ บังคับลำดับ — Contact ขั้นที่ 1 → Contact ขั้นที่ 2 → Business information
เงื่อนไขผ่าน ดูแค่ว่าหลอดความคืบหน้าเขียวเต็มทั้งสองฝั่ง แต่ละขั้นต้องผ่านเองก่อน ขั้นถัดไปจึงถูกปลดล็อก — หลอดเต็มอย่างเดียวไม่พอถ้าลำดับไม่ถูก
สถานะขั้นถัดไป เปิดให้แก้ไขได้ตลอด disabled จนกว่าขั้นก่อนหน้าจะสำเร็จ · ต้องบอกด้วยว่าติดอยู่ที่ขั้นไหนและต้องทำอะไรต่อ
ปุ่ม “Validate”
ใน New Job		 เปิดเมื่อข้อมูลครบ เปิดเมื่อผ่านครบ ตามลำดับ ทั้ง 3 ขั้น — บังคับที่ backend ไม่ใช่แค่ disable ปุ่มใน UI · กดได้เมื่อไหร่ = เข้า Ad Validate ได้เมื่อนั้น

Contact · ขั้นที่ 1

เชื่อม Line OA ลูกค้า

  • ผูก Line OA ของลูกค้าเข้ากับระบบ — เป็นขั้นแรกสุดเสมอ ไม่มีทางข้าม
  • ต้องเก็บผลลัพธ์การเชื่อมเป็นสถานะจริง ไม่ใช่แค่ checkbox ที่ผู้ใช้ติ๊กเอง
  • ถ้ายังไม่สำเร็จ ขั้นที่ 2 ต้องอยู่ในสถานะ disabled

Contact · ขั้นที่ 2

เชื่อมต่อ Plus AdTech

  • ปลดล็อกหลังขั้นที่ 1 สำเร็จเท่านั้น
  • เมื่อครบทั้ง 2 ขั้นแล้ว Contact ถือว่าผ่าน และ Business information จึงเปิดให้กรอก
  • เชื่อมโยงกับ P-025 / P-028 ในภายหลัง — script health และ event conflict ของ Plus AdTech

ขั้นที่ 3

Business information

  • กรอกให้ครบทุก field ที่จำเป็นตามที่ New Job ส่งมาเป็น requirement
  • ครบแล้ว precondition จึงผ่าน และปุ่ม “Validate” ใน New Job ถึงใช้งานได้
  • ยังต้องรองรับกรณีข้อมูลถูกแก้ทีหลัง — ถ้าไม่ครบอีกครั้ง ต้องกลับไปสถานะล็อก

ผลที่ตามมาของการย้าย gate นี้ไปไว้ใน New Job: เมื่อ Ad Validate ถูกเปิดขึ้นมา ข้อมูล Contact และ Business ต้องครบอยู่แล้วเสมอ — Ad Validate จึงไม่ใช่ที่ที่ผู้ใช้จะมารู้ตัวว่าข้อมูลขาด สิ่งที่ Ad Validate ตรวจคือ ตัว contract ที่รับมา ตาม FR-01 เท่านั้น (ดู §02)

02 / Flowchart · v2

Flow ภายใน Ad Validate — ตรวจแบบ background + คิวรอส่งตรวจ

สิ่งที่เปลี่ยนจาก v1 (กล่องที่มีป้าย NEW): ① ทุกรอบตรวจที่ผู้ใช้กดเอง ทั้ง “เริ่มตรวจ” และ “ส่งตรวจสอบใหม่” รันใน background ไม่มีหน้า Loading บล็อกอีก ② การแก้ไขแล้วกด Apply จะเก็บเป็น draft ในคิว ยังไม่ยิงไปที่ platform จนกว่าจะกด “ส่งตรวจสอบใหม่” จากนั้นระบบยิงการแก้ไขทั้งชุด แล้วตรวจใหม่ทั้งชุด ③ เมื่อตรวจเสร็จ แจ้งคนที่กดผ่าน In-app + LINE OA XPluser (ใช้ Email ถ้าส่ง LINE ไม่สำเร็จ) ④ Cron 00:00 ยังรันตามเวลาเดิม เป็น full re-scan แต่ไม่ยิง draft แทนผู้ใช้

จุดที่ต้องระวังตอน implement: กดซ้ำ / request ถูกยิงซ้ำ ต้องได้ run เดิม (idempotency key = job_id + draft set hash) · ถ้า cron กำลังรันอยู่แล้วผู้ใช้กดส่งตรวจ รอบของผู้ใช้เข้าคิวต่อท้าย ไม่ยกเลิกรอบ cron

03 / Flowchart

Gate logic — อะไรตัดสินว่าปุ่ม “ดำเนินการต่อ” กดได้

Logic นี้ถอดมาจาก vGate() ใน prototype และต้องถูกบังคับที่ backend ไม่ใช่แค่ซ่อนปุ่มใน UI (PRD FR-06) · เงื่อนไขทุกข้อถูกกรองด้วย vActiveChecks() ก่อน — rule ที่มี visibleIf แล้ว dependency ยังไม่ผ่าน จะไม่ถูกนับในทุกกรณี

Gate statusปุ่มดำเนินการต่อเงื่อนไขและสิ่งที่ระบบต้องทำ
not_runปิดยังไม่มีผล scan หรือผลหมดอายุ — PRD เสนอ scan expiry เริ่มต้น 24 ชม. (ยังรอยืนยันกับ Tech Lead)
blockedปิดมี active finding ที่ state = fail และ sev = crit อย่างน้อย 1 ข้อ · ต้องปฏิเสธที่ backend policy ไม่ใช่แค่ disable ปุ่ม
passed_with_warningsเปิดเมื่อยืนยันไม่มี Critical แล้ว แต่ยังเหลือ fail (warn/info) หรือ manual · ต้องมี confirmation + audit event พร้อม actor, reason, timestamp
passedเปิดactive checks ทุกข้อเป็น pass หรือ na
04 / Flowchart

P-027 · Conversion Tag Method — เงื่อนไขที่เข้มที่สุด

ชื่อ rule บอกว่า “ตรวจ 2 จุด” — จุดที่ 1 คือระบบตรวจแหล่งที่มาอัตโนมัติจากลายเซ็นใน Google Ads API (ตรงกับ Plus AdTech หรือไม่ ถ้าไม่ตรงระบบจะสันนิษฐานไว้ก่อนว่าเป็น GTM) และ จุดที่ 2 คือผู้ใช้ต้องเลือกยืนยันเองว่าสร้างจากเครื่องมือไหนจริง — ดูรายละเอียดเต็มที่ rule set reference · เงื่อนไขนี้ออกแบบมาเพื่อกันไม่ให้ใครพิมพ์เหตุผลแล้วกดผ่านโดยไม่มีผลตรวจจริงมารองรับ — ทางออก “ยืนยันเหตุผล” ของจุดที่ 2 มีอยู่เฉพาะตอนที่จุดที่ 1 เจอสัญญาณจริงเท่านั้น ถ้าไม่เจอสัญญาณเลย ไม่มีทางข้าม ต้องแก้การติดตั้งก่อนเท่านั้น · เปิดเงื่อนไขนี้ใน Prototype ↗

Conditional rule

P-028 ขึ้นกับ P-027

  • P-028 จะถูกประเมินก็ต่อเมื่อ P-027 state = pass และ trackingMethod = adtech
  • ถ้าทีมยืนยันใช้ GTM Manual แทน P-028 จะไม่ปรากฏและไม่ถูกนับใน gate
  • Rule ที่ไม่ผ่าน visibleIf ต้องไม่นับเป็น fail และไม่นับเป็น pass — มันไม่อยู่ใน run นี้

Remediation

สามทางแก้

  • auto_fix — ระบบ preview การเปลี่ยนแปลง แล้วยิง platform mutation หลังผู้ใช้ยืนยัน
  • external_fix — เปิด deep link ไป Ads Manager / GTM แล้วให้ผู้ใช้สั่ง re-scan เอง
  • exception — ต้องมี permission + เหตุผล + หลักฐานจากผลตรวจจริง

Edge cases

ต้องออกแบบรองรับ

  • Mutation สำเร็จแต่ re-scan ยังเห็นค่าเดิม (eventual consistency)
  • ผู้ใช้สองคนแก้ finding เดียวกันพร้อมกัน
  • Rule set ถูก publish ใหม่ระหว่าง run — run เดิมต้องยึด version เดิม
  • Upstream job ถูกยกเลิกขณะกำลัง scan

06 / Layer stack

โครงสร้างของโปรเจค

Ad Validate แยก repository และ lifecycle ออกจาก Plug AI New Job — ชั้นบนสุดคือ contract ที่คุยกับ upstream ส่วนชั้นล่างลงไปเป็นของ Ad Validate ทั้งหมด · ข้อห้ามหลัก: ไม่อ้าง DOM, state หรือ business logic ภายใน Plug AI New Job โดยตรงในทุกชั้น

สิทธิ์ทำอะไรได้
Operatorรัน scan · ดูผล · ใช้ auto-fix เท่าที่อนุญาต · re-scan
Reviewer / Leadทุกอย่างของ Operator + อนุมัติ Warning หรือ Manual exception
Adminจัดการ credentials · เปิด-ปิด rule · rollout rule set version ใหม่
Service accountส่ง job context เข้ามา และรับ completion outcome กลับ — ทำอย่างอื่นไม่ได้

ยังเป็น open decision ก่อนเริ่ม build: backend stack และที่อยู่ repository, Ad Validate จะเป็น service ใหม่หรือ module ใน Plus AdTech backend, เจ้าของ credential และ token refresh strategy, source of truth ของ job/account mapping, rule management จะเป็น code config หรือ admin UI, scan expiry ที่เหมาะสม และใครมีสิทธิ์ approve exception
