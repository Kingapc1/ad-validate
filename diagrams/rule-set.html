01 / Architecture

วิธีอ่าน rule หนึ่งข้อ

ทุก rule ไม่ว่าแพลตฟอร์มไหน เดินผ่านเส้นทางเดียวกัน — ดึงข้อมูลจากแหล่งใดแหล่งหนึ่ง (หรือหลายแหล่ง) มาทำเป็น snapshot, ส่งให้ evaluator ประเมินตาม rule set เวอร์ชันที่ผูกกับ run นั้น, ได้ finding ที่มีทั้งสถานะและความรุนแรง แล้วจึงเสนอวิธีแก้ · สิ่งที่ต่างกันระหว่าง rule คือแหล่งข้อมูลและวิธีแก้ ไม่ใช่เส้นทาง

ความรุนแรง — ตัวที่ตัดสินว่างานไปต่อได้ไหม

ระดับผลต่อการไปต่อความหมาย
Criticalบล็อกถ้าไม่แก้ = ออนไลน์ไม่ได้ · backend ต้องปฏิเสธการกดดำเนินการต่อ ไม่ใช่แค่ซ่อนปุ่มใน UI
Warningผ่านได้เมื่อยืนยันควรแก้ก่อนออนไลน์ · ข้ามได้แต่ต้องมีผู้มีสิทธิ์ยืนยัน และบันทึก actor + เหตุผล + เวลา
Infoไม่บล็อกแนะนำให้ปรับเพื่อผลลัพธ์ที่ดีขึ้น
Manualนับเป็นค้างเป็นสถานะของ finding ไม่ใช่ระดับความรุนแรง — ต้องมีคนตรวจหรือแนบหลักฐาน และถูกนับรวมกับ Warning ตอนตัดสิน gate
Not applicableไม่นับไม่เกี่ยวกับงานนี้ เช่น rule เฉพาะ Display เมื่องานเป็น Search ล้วน · ไม่นับเป็นทั้ง pass และ fail

วิธีตรวจ — ระบบตัดสินเองได้แค่ไหน

ประเภทความหมาย
อัตโนมัติระบบตัดสินผ่าน/ไม่ผ่านได้เองทั้งหมดจากข้อมูลที่ดึงมา ไม่ต้องรอคน
กึ่งอัตโนมัติระบบดึงข้อมูลและเสนอผลให้ แต่เกณฑ์ตัดสินเป็นดุลพินิจของทีม ต้องมีคนกดยืนยัน
ตรวจเองต้องมีคนตรวจและแนบหลักฐาน ระบบไม่ตัดสินให้

แหล่งข้อมูล — ดึงจาก API หรือต้องเปิดเว็บไปดู

แหล่งระบบทำอะไร
Ads API · อ่านดึงผ่าน API ของแพลตฟอร์มอย่างเดียว ไม่เขียนกลับ — ต้องมี credential ที่อ่านบัญชีนั้นได้
Ads API · อ่าน + เขียนดึงผ่าน API และยิง mutation กลับไปแก้ที่แพลตฟอร์มได้ — เป็นกลุ่มเดียวที่ทำ auto-fix ได้จริง
สแกนหน้าเว็บไซต์Ad Optimizer โหลดหน้าเว็บจริง (landing / thank-you) แล้วตรวจ script tag, จำนวน loader และ event ที่ยิงออก — ไม่ผ่าน API ใดเลย
GTM API · อ่านอ่าน container ของเว็บไซต์เป้าหมายเพื่อ list tag และ trigger — อ่านอย่างเดียว แก้ให้ไม่ได้
Plus AdTech APIอ่าน event configuration ที่ตั้งไว้ฝั่ง Plus AdTech เพื่อเทียบกับ GTM
ข้อมูลใน DMS / New Jobเทียบกับค่าที่รับมาจาก job context เช่น Expect Date หรือ tracking method ที่ทีมเลือกไว้
ต้องมีคนยืนยันระบบดึงข้อมูลให้ได้ แต่เกณฑ์ตัดสินเป็นดุลพินิจของทีม

วิธีแก้เมื่อไม่ผ่าน

ประเภทขั้นตอน
ระบบแก้ให้ได้ระบบ preview การเปลี่ยนแปลงให้ดูก่อน ผู้ใช้กดยืนยัน แล้วระบบยิง mutation ไปแก้ที่แพลตฟอร์ม · ต้องบันทึก before/after และประเมินซ้ำ
ทีมแก้นอกระบบเปิด deep link ไป Ads Manager / GTM / เว็บไซต์ ให้ทีมแก้เอง แล้วกลับมากด “ตรวจซ้ำ”
ยืนยันข้าม (exception)ต้องมี permission, เหตุผล และหลักฐานจากผลตรวจจริง · ห้ามใช้ข้ามกรณีที่ไม่พบสัญญาณใดทำงานเลย
ไม่มี actionผ่านหรือไม่ผ่านตามผลตรวจอย่างเดียว ไม่มีปุ่มแก้ในหน้านี้

กฎที่ใช้กับทุก rule: หนึ่ง run ผูกกับ rule-set version เดียวตลอดอายุของมัน — ถ้ามีการ publish rule ใหม่ระหว่างทาง run เดิมต้องยังแสดงผลด้วยเวอร์ชันเดิมเสมอ ไม่ประเมินใหม่ย้อนหลัง

Resource: conversion_action (2 query — ห้ามรวม metrics.conversion_last_* กับ segments.date เพราะ Google คืน [] โดยไม่แจ้ง error)
-- Q1 inventory + วันที่ล่าสุด (ไม่มีช่วงวันที่)
SELECT
  conversion_action.id,
  conversion_action.name,
  conversion_action.status,
  conversion_action.category,
  conversion_action.origin,
  conversion_action.primary_for_goal,
  conversion_action.type,
  metrics.conversion_last_conversion_date,
  metrics.conversion_last_received_request_date_time
FROM conversion_action
WHERE conversion_action.status = 'ENABLED'

-- Q2 จำนวน conversion ใน lookback
SELECT conversion_action.id, metrics.all_conversions
FROM conversion_action
WHERE segments.date DURING LAST_30_DAYS

conversion_action.originenumป้ายที่อิงเวลาและ Tag fires, no conversions ใช้ได้เฉพาะ WEBSITE

metrics.all_conversions (30 วัน)double≥ 1 = Receiving signals ทันที

Logic (ต่อ action, ป้ายหลัก 1 ป้าย ที่เหลือเป็น related): conversion ≥ 1 ใน 30 วัน → Receiving signals · conversion = 0 และ (clicks < 20 หรือ action อายุ < 7 วัน) → Need more data · Website + tag ยิงภายใน 3 วัน → Tag fires, no conversions · Website เงียบ > 14 / > 7 / > 3 วัน → Possibly inactive (Broken) / Stale signal / Signal delayed · origin อื่น → Need more data · เกณฑ์ทั้งหมดอ่านจาก config ชุดเดียวกับ Ad Optimizer ลำดับจริงยึดโค้ด conversion-tag-health.domain.ts
Verdict ของการ์ด: Primary Broken → Critical · Needs attention → Warning · Need more data ทั้งหมด → ผ่าน (รอยืนยันหลังออนไลน์)
